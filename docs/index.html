leat

The lakehouse gave us great storage. But running the everyday 90% of ETL still means spinning up a cluster. leat is the missing piece: Kafka-style incremental ETL over Iceberg & Delta — on one node, for a fraction of the cost.

View on GitHub → Quickstart

00The story

A lakehouse table — Iceberg or Delta — is already an append log. Every commit is a new snapshot. Add a monotonic offset and "read what changed since last time" becomes "read rows past my last offset." That's a Kafka consumer — except the topic is a table you already have.

So here's the thing that started leat: if the table is already a log, why does every incremental bronze → silver → gold job still spin up a distributed engine to process a delta that fits on one core? You end up renting a cluster to filter two million rows — and paying for it to sit warm between runs.

leat isn't a Spark killer. It's a Spark-is-overkill killer — for the ~90% of ETL that's small, frequent, incremental batches.

But "run it on one node" was just the start. Once we pulled that thread, a whole pile of ecosystem papercuts came with it — fragile exactly-once, offsets you babysit, streaming jobs you can't scale or deploy, format lock-in, append-only pipelines that shatter the moment data mutates. So we set out to fix each one. Here's the list.

01The problems we set out to solve

Every card is a real pain in today's lakehouse-compute stack — and what leat does about it. Everything marked tested ships with a test in the repo.

✕ Overkill

Renting a cluster to filter 2M rows

Most medallion ETL is tiny incremental batches — overhead you pay for and never use. leat runs the same transform on one node: same result, ~4.6–9.4× less CPU, and it scales to zero between runs.

measured
✕ Silent duplicates

Exactly-once that quietly isn't

The classic bug: your offset lives in a separate checkpoint store; a crash between "data landed" and "offset saved" replays a batch. leat commits the offset inside the sink's own snapshot — it advances if and only if the data does. One atomic step, no window.

tested
✕ Boilerplate

Offsets you have to babysit

Manual offset columns, checkpoint locations, auto.offset.reset. leat gives you Kafka's ergonomics — earliest/latest, seek, lag — but mints and manages the offset for you. Your transforms see only your columns.

tested
✕ Stateful monolith

A streaming job you can't scale or deploy

Spark streaming pins its state to one running job — scaling is a cluster resize + restart, and there's no clean blue-green. leat keeps state in the sink, so compute is disposable: scale out = deploy an instance, scale in = remove one, deploy green beside blue.

demonstrated
✕ Lock-in

Married to one table format

Pick Iceberg or Delta and your tooling picks a side. leat is format-neutral (both first-class, same code) and catalog-neutral (SQLite, REST, Glue, Unity) — proven live against a REST catalog + object store, with concurrent writers.

proven live
✕ Append-only

Great — until your data mutates

Append-only pipelines break the moment a row updates or a delete lands. leat has an upsert mode (merge-by-key, idempotent) and an on_change safety check that surfaces mutations append mode can't see — with full CDC/deletes on the roadmap.

02The receipts: cost

On the identical result (byte-for-byte, parity-checked) of a realistic medallion DAG, leat used ~4.6–9.4× fewer CPU-seconds than Spark. CPU-seconds are what your cloud bill is made of.

A pipeline that runs every few minutes is a cluster rented 24/7 (or a 3-second JVM cold start every trigger) vs. a task that runs ~0.4 s and exits. That gap is structural, not a micro-optimization.

04Scale like a stateless service

Because the offset lives in the sink's commit, a worker holds no durable state — so scaling and deploys stop being cluster surgery and become ordinary devops.

Scale = replica count

Scaling out is deploying another instance; scaling in is removing one. No cluster resize, no restart, no state migration. kubectl scale --replicas=8, and anonymous workers self-distribute the partitions — a dead one's work is reclaimed from the sink offset, exactly-once.

Blue-green, not stop-the-world

Deploy a green version writing to a new sink, parity-check it against blue, and flip which one downstream reads. No checkpoint-compatibility landmines, no downtime — the thing Spark streaming makes miserable.

05How to use it

If you know Polars, you know leat. Write a DataFrame; the offset is managed for you.

# pip install "git+https://github.com/samtheprogrammer/leat.git"
import leat, polars as pl

lt = leat.connect("/data/leat")
lt.table("db.events").write(pl.DataFrame({"user_id":[1,2,3], "value":[50,150,250]}))

@lt.model(source="db.events", sink="db.silver", start="earliest")
def silver(df):                      # df is just your columns — no _offset
    return df.filter(pl.col("value") > 100)

silver.run(once=True)                # incremental, exactly-once, done
print(lt.table("db.silver").read())  # Polars out — and it reads like a Kafka consumer
